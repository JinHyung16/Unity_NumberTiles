# NumberTiles

> Unity 기반 모바일 숫자 퍼즐 — **1인 기획·개발 프로젝트 (기획 / 클라이언트 / 데이터 파이프라인)**

| 규모 | |
|---|---|
| 스테이지 수 | **300** (1~300 모두 디자인 완료) |
| 라인 종류 (StageLevel) | 41종 (한 칸짜리부터 9칸 줄까지) |
| 특별 맵 | 12종 (10스테이지마다 등장) |
| 굵직한 분기 스테이지 | 6개 (50/100/150/200/250/300) |
| 스킬 (아이템) | 4종 |

<br>

## 프로젝트 개요

사과 게임이 유행하던 시기, **"왜 이 게임이 재밌는가?"** 라는 코어 재미 분석을 출발점으로 시작했습니다. 분석 중 발견한 **Number Tiles** 장르에서 동일한 재미 구조를 확인했고, 이를 직접 구현하며 게임의 재미 설계를 검증했습니다.

목표는 단순 클론이 아니라 다음 세 가지를 1인이 끝까지 완성해 보는 것이었습니다.

1. **코어 루프 설계** — 매칭/클리어/실패의 재미 분석과 재현
2. **운영 가능한 레벨 디자인** — 300 스테이지의 난이도 곡선과 신선함
3. **데이터 파이프라인** — 코드 빌드 없이 밸런싱이 가능한 워크플로우

<br>

## 코어 재미 분석

| 요소 | 설명 |
|------|------|
| **낮은 진입 장벽** | 같은 숫자 또는 합이 10이 되는 두 숫자를 연결하는 단순한 규칙 |
| **전략적 판단** | 스테이지별 고유한 맵 형태(StageLevel)에 따라 어떤 라인을 먼저 지울지 신중하게 선택 |
| **두뇌 활성화 경험** | 힌트 없이 스스로 경우의 수를 계산하는 과정에서 "똑똑해지는 느낌"을 제공 |
| **승부욕 자극** | 스테이지가 올라갈수록 맵 복잡도가 증가하며 클리어 시 성취감과 도전 욕구 유발 |

<br>

## 게임 규칙

- **매칭 조건**: 두 숫자가 같거나, 합이 10
- **이동 방향**: 가로 / 세로 / 대각선 / 행 끝→다음 행 시작 (flat row-major)
- **경로 조건**: 두 타일 사이 활성 타일이 없어야 연결 가능
- **클리어 조건**: 보드에 등장했던 숫자 1~9가 모두 제거됨
- **실패 조건**: 줄 추가 아이템이 없고 매칭 가능한 쌍이 남아있지 않음

<br>

## 레벨 디자인

### 기획 의도 — 맵 모양 하나로 난이도와 신선함을 같이 해결

처음 잡은 질문은 두 개였습니다. **"난이도를 어떻게 올릴 것인가"** 와 **"어떻게 안 질리게 할 것인가"**. 이 둘을 따로 풀려면 변수가 두 개가 되고, 데이터도 운영도 복잡해집니다.

대신 **맵 모양(StageLevel 조합) 하나로 둘 다 처리**하기로 했습니다.

- 타일 수는 그냥 점점 많아질 뿐 — 양만 늘어나는 단순한 압박
- **맵 모양은 좁은 줄을 섞을수록 어려워지고, 모양이 매판 다르면 그 자체로 새로 보입니다**

결과적으로 시트의 `StageLevel` 한 컬럼만 다듬어도 난이도와 신선함이 같이 움직여서 운영이 단순해집니다.

### 세 가지 원칙

| 원칙 | 어떻게 |
|------|--------|
| **천천히 어려워지다가 가끔 확 어려워짐** | 타일 수는 로그 곡선으로 부드럽게, 25/50 스테이지마다 살짝/크게 튀게 |
| **모양이 곧 난이도** | 9칸짜리 넓은 줄(쉬움)부터 1칸 줄(어려움)까지, 진행에 따라 점점 좁은 줄을 섞음 |
| **질릴 때쯤 한 번씩 환기** | 10스테이지마다 평소와 다른 형태의 맵을 끼워 넣어 패턴 피로를 끊음 |

### 타일 수 곡선 (Stage 1~300)

타일 수는 그냥 양만 늘어나는 변수라 단순한 로그 함수 + 주기 보정으로 처리.

```
SpawnTileCount(n) = round( 47.74 * ln((n+20)/21) ) + 30   // 30 → 160
```

| 구간 | 보정 | 의도 |
|------|------|------|
| 평상시 | × 1.00 | 부드럽게 오름 (초반은 빠르게, 후반은 천천히) |
| 25스테이지마다 | × **1.10** | 살짝 어려운 판 — 가벼운 긴장 |
| 50스테이지마다 | × **1.20** | 확 어려워지는 판 — 큰 분기, 특별 맵과 같이 등장 |
| 그 다음 판 | × **0.92** | 한숨 돌리는 휴식 |

### 진행에 따라 어떤 라인이 등장하는가

스테이지가 올라갈수록 **사용하는 라인 종류**가 넓은 줄에서 좁은 줄, 한 칸짜리까지 점점 늘어납니다. 타일 수가 같아도 좁은 줄이 섞이면 매칭이 까다로워져 자연스럽게 어려워집니다.

| 구간 | 스테이지 | 사용하는 라인 | 라인 성격 | 한 판당 라인 수 |
|------|---------|--------------|----------|----------------|
| 1 | 1~20 | id 1~5 | 9칸 넓은 줄만 | 2~3 |
| 2 | 21~50 | id 1~10 | 6~8칸 줄 추가 | 3~4 |
| 3 | 51~100 | id 1~21 | 4~5칸 좁은 줄 등장 | 4~6 |
| 4 | 101~175 | id 1~28 | 3칸 줄까지 | 5~8 |
| 5 | 176~250 | id 1~36 | 2칸 줄까지 | 6~9 |
| 6 | 251~300 | id 1~41 | 1칸짜리 단일 셀까지 | 7~11 |

### 10스테이지마다 한 번씩 — 특별한 모양의 맵

평소 스테이지는 그 구간의 라인을 조합해 만들지만, 10스테이지마다는 **모양이 정해져 있는 맵 12종**을 돌아가며 배치합니다. 룰은 그대로지만 보드 모양이 확 달라서 "어, 맵이 다르네" 하고 환기가 되고, 익숙해진 패턴 피로가 끊깁니다.

| # | 이름 | 모양 |
|---|------|------|
| 0 | 피라미드 | 좁→넓→좁 (대칭) |
| 1 | 모래시계 | 넓→좁→넓 |
| 2 | 사다리 우향 | 위치 슬라이드 |
| 3 | 사다리 좌향 | 반대 슬라이드 |
| 4 | 벽 | 꽉찬 직사각형 |
| 5 | 양옆 절벽 | 좌끝/우끝 번갈아 |
| 6 | 외딴섬 | 한 칸짜리 줄 모음 |
| 7 | 돔 | 가운데가 좁아짐 |
| 8 | 체스판 | 넓은 줄/좁은 줄 교차 |
| 9 | 계단식 좁아짐 | 단조 감소 |
| 10 | 거울 대칭 | 좌우 대칭 |
| 11 | 방울방울 | 좁/넓 교차 |

같은 모양이라도 진행에 따라 **줄 수가 점점 늘어납니다**. 예를 들어 "벽"은 초반엔 6~7줄, 후반엔 14줄로 등장 → 같은 모티브를 후반까지 재활용하면서 부담은 점점 키움.

### 굵직한 분기 스테이지 (50 / 100 / 150 / 200 / 250 / 300)

따로 보스 같은 시스템은 두지 않았습니다. 대신 50스테이지마다 한 번씩 **타일 수 +20% + 풀사이즈로 등장하는 특별 맵**을 배치해, "지금 구간이 바뀐다"는 감각을 주려고 했습니다.

| Stage | 들어간 맵 | 의도 |
|-------|----------|------|
| 50 | 풀사이즈 피라미드 | 첫 큰 분기, 룰 잘 익혔는지 점검 |
| 100 | 풀사이즈 모래시계 | 두 번째 분기 |
| 150 | 무지개 (한 칸 줄까지 동원) | 새로운 시각 자극 |
| 200 | 다이아몬드 | 마름모 모양 |
| 250 | 나선 | 회전하는 흐름 |
| 300 | 마스터 (24줄, 전 패턴 조합) | 엔딩 |

## 스킬 (아이템) 시스템

각 스테이지 시작 시 모든 아이템을 3개씩 보유합니다. 바로 쓰는 것과, 토글로 켜놓고 타일/행을 클릭해서 쓰는 것 두 종류로 나뉩니다.

| 아이템 | 사용 방식 | 설명 | 의도 |
|--------|----------|------|------|
| **AddTiles** | 즉시 | 보드 빈 칸에 새 숫자 타일을 한 번에 스폰 (한 번에 20개) | 막혔을 때 다시 풀리게 — 실패 회피 |
| **BreakOneTile** | 토글 → 타일 클릭 | 클릭한 타일 1개 제거 | 한 점만 콕 집어 정리 |
| **LineSwap** | 토글 → 행 두 번 클릭 | 두 행을 통째로 바꿔치기 | 보드 구도 자체를 바꾸는 전략 카드 |
| **DiagonalClear** | 토글 → 셀 클릭 | 그 셀이 속한 ↖↘ 대각선 위 타일 전부 제거 | 광역 정리 + 게임 룰의 대각선 매칭 강조 |

토글 켜면 무장, 끄면 취소. 다른 토글을 켜면 이전 토글은 자동으로 꺼져서 한 번에 하나만 무장됩니다. 사용이 끝나면 토글도 같이 풀립니다.

## 데이터 운영 파이프라인

스테이지/맵 정의는 **Google Spreadsheet**에서 관리됩니다. 코드 빌드 없이 시트 편집만으로 밸런싱이 즉시 반영되도록 OAuth2 기반 자동 동기화 + 코드 생성 파이프라인을 구축했습니다.

```
Google Spreadsheet ──(OAuth2 / Sheets+Drive API)──► CSV
                                                    │
                                                    ▼
                                       SheetJsonConverter (CSV → JSON)
                                                    │
                                                    ▼
                                Assets/Resources/GoogleSheetData/*.json
                                                    │
                                                    ▼
                              DataManager.GetContainer<T>() (런타임 로드)

                  + DataContainerCodeGenerator (열 정의 기반 컨테이너 클래스 자동 생성)
                  + EnumCodeGenerator (지정 시트 → C# enum 자동 생성)
```

| 시트 | 컬럼 | 역할 |
|------|------|------|
| `Stage` | `id`, `SpawnTileCount`, `StageLevel(intArray)` | 스테이지별 타일 수 + 사용할 라인 패턴 시퀀스 |
| `StageLevel` | `id`, `StartColumn`, `EndColumn` | 한 행의 활성 컬럼 범위(보드 모양 단위) |

**Editor 도구**: `Tools/Google Sheet Data Loader` 윈도우에서 OAuth2 인증 → `구글 시트 DB 최신화` 버튼 한 번으로 동기화 → 자동 JSON 변환 + Type-safe 컨테이너 코드 생성. refresh token으로 1회 로그인 후 재인증 불필요.

## 아키텍처 및 구현 특징

### 1. Observer 패턴 — 보드 상태와 UI 분리
`ITileObserver` / `TileNotify`로 모든 보드 변경 이벤트를 구독자에게 전달. `GameManager`는 `BoardChanged`/`ItemCountChanged` 알림으로 결과 판정, `TileWindow`는 셀 단위 알림(`CellValueChanged`/`CellOpenChanged`/`CellSelectedChanged`)으로 부분 갱신만 수행하여 불필요한 UI 재생성을 회피.

```
TileManager ──(TileNotify)──► ITileObserver (GameManager, TileWindow, StageItemGroup)
```

### 2. Factory 패턴 — 아이템 시스템 확장성
`IItemFactory` / `ITileItem`로 아이템 종류를 추상화. 새로운 아이템은 `ItemType` 추가 + 클래스 1개 + Factory 케이스 1줄로 확장. 즉시형/타겟형 모두 동일 인터페이스로 처리.

```
TileItemFactory.Create(ItemType) → ITileItem.Execute(IFactoryInput) → IFactoryOutput
```

### 3. 매칭 알고리즘 — 4방향 경로 검사
방향별 독립 함수로 분리해 각 로직을 단일 책임화. 빈 셀 경유는 허용하되 활성 타일은 차단하는 규칙을 방향마다 명시적으로 정의.

| 함수 | 방향 |
|------|------|
| `IsBlockedOnRow` | 가로 |
| `IsBlockedOnCol` | 세로 |
| `IsBlockedOnDiagonal` | 대각선 |
| `IsBlockedOnFlatRowMajor` | 행 끝 → 다음 행 시작 (row-major wrap) |

### 4. 진행 상황 자동 저장/복원 (보드 형태 검증 포함)
`GameProgressData`(JSON)에 보드 상태와 함께 **shape hash**를 저장. 앱 재시작 시 시트 변경으로 스테이지 형태가 달라졌으면 복원을 거부하고 새로 시작 → 데이터 변경에 따른 충돌 방지.

```
GameProgressSaver.Build() → JsonUtility.ToJson() → 로컬 파일
GameProgressSaver.TryLoad() → TileManager.TryApplyProgress() → shape hash 검증 → 복원
```

### 5. Object Pooling
`PoolManager`가 `TileUIComponent`를 `Stack<T>` 기반으로 관리. 사전 워밍(Prewarm 100개)으로 런타임 `Instantiate` 호출 최소화.

### 6. GC 최적화
- 랜덤 스폰 후보 배열(`_digitCandidates`)을 멤버 변수로 사전 할당 — 핫패스의 `new int[]` 제거
- `List<int>` → `Queue<int>`로 AddTiles 큐의 Dequeue O(n) → O(1) 개선
- 숫자 추적 배열(`_digitSeen`/`_digitCleared`/`_digitCount`)을 `Array.Clear`로 재사용

### 7. 토글과 무장 상태 동기화
아이템 토글이 ON이면 무장, OFF면 취소. 다른 토글이 켜지거나 효과가 발동되면 켜져 있던 토글은 자동으로 꺼집니다. UI는 매니저를 직접 호출하지 않고 `IListener`를 통해서만 무장/취소를 요청하고, `_syncing` 가드로 동기화 콜백이 무한 루프를 만들지 않도록 처리.

## 개발 의도

장르 클론이 아니라 **"이 게임이 왜 재밌는가"** 를 먼저 분석하고, 그걸 바탕으로 300 스테이지를 직접 짜고, 시트로 운영할 수 있는 환경까지 한 명이 끝까지 만들어 보는 게 목적이었습니다. 기획 / 코드 / 데이터 도구가 한 프로젝트 안에서 어떻게 맞물리는지 체감해 보고 싶어 시작한 프로젝트입니다.
